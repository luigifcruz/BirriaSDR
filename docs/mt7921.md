# The MT7921 receiver: MT7961 and MT7972

The implemented receiver is the COMFAST USB dongle `3574:6211`, which combines
an MT7961 digital die with an MT7972 analog die. The backend is named `mt7921`
after the USB product family. Boards with MediaTek's generic ID `0e8d:7961`
and the same dies, such as the EDUP AX3000, are also supported. This page
describes its current configuration, register fields and data path.

## Supported configuration

| Property | Implemented value | Scope |
| --- | --- | --- |
| Board | COMFAST `3574:6211` or generic `0e8d:7961`, digital ID `0x7961`, analog ID `0x79728a10` | Other boards and die revisions are not enabled |
| Receive chain | Chain 0 | Chain selection is not the same as antenna connector selection |
| Center frequency | 2156 to 2610 MHz inclusive, or 2190 to 2610 MHz on generic-ID boards. Default 2437 MHz | Programming range only. Sensitivity across the range is uncalibrated |
| Tuning resolution | Nominal 28.6102294921875 Hz with integer-Hz requests | Uses the full 20-bit fraction. Physical fine-step response and absolute accuracy are unmeasured |
| Complex sample rate | 40 MSps, fixed | Lowest validated native rate. No other rate is exposed |
| Receive filter | Matched nominal 40 MHz analog and digital profile | Finite rolloff and alias rejection, with no independent bandwidth control |
| Sample format | Signed 14-bit I and Q in 16-bit slots | Each complex sample occupies four bytes |
| Live controls | Center frequency, manual gain codes and gain override mode | Changes disturb samples, and no exact transition sample is reported |
| Device program | Original 1,120-byte RAM download | Uses the immutable factory ROM. No vendor RAM firmware or patch is downloaded |
| Host support | Linux and macOS code paths | Hardware validation covers only the Raspberry Pi 5 |

The receive path looks like this:

```mermaid
flowchart LR
    rf["RF/PHY chain 0"] --> icap["ICAP"]
    icap --> sram["Circular SRAM"]
    sram --> dma["Device DMA"]
    dma --> usb["USB"]
    usb --> host["Host I/Q"]
```

## Register access

A register's address includes its access space and bank. Equal numeric offsets
in different banks refer to different hardware. The tables describe the fields
the driver owns and their current values. When changing them, preserve
unrelated bits and keep the ordering used in the implementation.

Each access name corresponds to a path in [usb.c](../src/usb.c):

| Access name | Read type/request | Write type/request | Meaning |
| --- | --- | --- | --- |
| MMIO | `0xdf / 0x63` | `0x5f / 0x66` | Digital registers and mapped device memory |
| UHW | `0xde / 0x01` | `0x5e / 0x02` | Host-wrapper path for USB, including reset |
| Bridge | `0xc0 / 0x63` | `0x40 / 0x66` | Registers of the RF SPI controller |
| RF ports 0 and 1, TOP port 5 | Through Bridge | Through Bridge | Analog register offsets, not direct host MMIO |

The direct requests transfer a four-byte little-endian value, with address bits
`[31:16]` in `wValue` and `[15:0]` in `wIndex`. The analog helper encodes the
physical port in command bits `[15:13]`, the read flag in bit 12 and an aligned
register offset in `[11:0]`, then writes DATA to launch the transaction.

The physical analog ports have these roles:

| Physical SPI port | Role in this profile |
| --- | --- |
| Port 1 | Active analog receive chain 0 |
| Port 0 | Companion bank whose secondary synthesizer supplies the selected local oscillator |
| Port 5 (TOP) | Shared analog clock, identity and control registers |

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| SPI busy status | Bridge `0x7c004000` | Bit 1 for Wi-Fi ports, bit 5 for TOP | Poll before and after each transfer |
| Wi-Fi SPI transaction | Bridge `0x7c004010 / 0x7c004014 / 0x7c004018` | Command / write data / read result | Shared by physical ports 0 and 1 |
| TOP SPI transaction | Bridge `0x7c004050 / 0x7c004054 / 0x7c004058` | Command / write data / read result | Physical port 5 |

## Preparing the device

The host restores the saved gain and filter fields, resets the Wi-Fi subsystem,
prepares the command transport and drains stale bulk input. The ROM patch
semaphore must report an unpatched device, meaning the acquire and release
results must be 2 and 3 respectively. A software reset does not remove a
retained vendor patch.

The original program is loaded at `0x00915000` through the immutable boot ROM.
It calls the PHY power-on helper at `0x00837142`, initializes its descriptor
ring and waits for GO. A fresh nonce and mailbox response confirm that it is
running. The host then configures capture, clocks, tuning, routing, gain and the
matched filter, and queues host reads before releasing GO. A STOP request
drains device DMA and stops capture. Cleanup retires host transfers, restores
the gain and filter fields and resets the subsystem. All changes are volatile,
and nothing is written to flash or eFuse.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Digital identity | MMIO `0x70010200` | Low 16 bits must be `0x7961` | Board identity is checked separately |
| Analog identity | TOP `0x02c` | Must read `0x79728a10` | Other analog revisions are not enabled |
| Wi-Fi subsystem reset | UHW `0x70002600` | Pulse bit 0 | Does not clear retained patches or all analog settings, so restore the saved gain and filter fields first |
| Endpoint reset options | UHW `0x74011890` | Clear mask `0x007003f0` before reset | Preserves the tested ROM handoff behavior |
| Reset completion | UHW `0x74000a20` | Wait for bit 22 after clearing `0x74000a24` | Other status bits are not interpreted |
| Firmware download engine | MMIO `0x54000808` | Write `0x80000000` to reset, then require `0x25` after download | Completion value is specific to this loader path |
| Download checksum | MMIO `0x54000814` | Require zero after image transfer | Delivery check, not proof of execution |

### Automatic startup and stream recovery

The startup path retries once after a transient preparation I/O error or
timeout, using a software USB reset and a complete reinitialization. Before
issuing new commands, it drains stale bulk input in 64 KiB reads, within time
and byte limits. It never clears halts on healthy endpoints, and it checks the
patch state again before loading the program.

When an application enables recovery, the asynchronous reader can restart with
the last committed frequency and gain. Each attempted restart reports a gap
before any resumed data. The number of lost samples is unknown, and delivered
sample indices remain cumulative counts rather than elapsed RF time. Live
setters return busy during reinitialization, and explicit cancellation prevents
another restart.

| Condition | Library behavior |
| --- | --- |
| Preparation I/O error or timeout | One software USB reset and a complete startup retry before sampling |
| Stream overrun, transient transport failure or failed live control | Stop and clean up, then restart only if a recovery budget and gap callback are enabled |
| Failed live setter | Keep the preceding committed settings and return the setter error, even if the reader later recovers |
| Finite read | Return an error rather than combine separate acquisitions |
| Retained vendor patch or unsupported configuration | Return an error with no fallback to vendor firmware |
| Removed device or reset-invalidated handle | Stop hardware access. The application must close the handle and rediscover the device |

The [public header](../include/birriasdr.h) defines the callback and threading
contracts. The [architecture guide](architecture.md#tests-and-firmware)
describes the lifecycle and recovery tests.

### Interpreting failed captures

The statistics identify the stage that was reached, not the failing register or
the full cause. A successful reset check does not guarantee that the next
transport operation will succeed.

| Report | Meaning |
| --- | --- |
| Firmware state 9 | Capture SRAM overran before transport released the samples |
| Host queue overrun | The application did not consume the bounded queue quickly enough, and the firmware state may be unavailable |
| Stage 2 | Failure in ROM transport preparation, before receiver configuration |
| Stage 5 during tuning | Possible frequency readback mismatch or rejected calibration diagnostic |
| Stage 5 before GO | Also covers filter setup and verification |
| Firmware state 3 after a failed live control | The requested stop completed, which does not show that the control succeeded |

## Receiving through RF/PHY chain 0

The analog front end mixes the input down to baseband, filters it and sets the
gain. The digital physical-layer path supplies the complex stream selected by
the capture tap. The full internal arrangement upstream of that tap is not
mapped, so the supported configuration uses the fields below together.

### Clocks and receive routing

The clock sequence establishes the analog references, switches the digital mux
and finishes the wake sequence before tuning. The strap-dependent TOP standby
bit must be cleared and verified before proceeding. The companion receiver uses
distinct enable values even though its synthesizer supplies the oscillator for
the active receiver.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Clock handoff | MMIO `0x70000148` | Set bit 4, poll bit 7, then later set bit 0 and clear bit 4 | The complete sequence also touches other clock registers |
| Wake-path strap | MMIO `0x70011094[2]` | Selects a temporary TOP standby sequence | Board-dependent input |
| Analog reference standby | TOP `0xb00[16]` | Clear before tuning, wait 20 microseconds and verify | Distinct from RF chain-bank `0xb00`. The exact circuit name is unknown |
| Receiver enables | RF ports 1/0 `0x1e4`, gate `0x1e8[31]` | Final values `0x3fb0b` / `0x23c1` with the gate set | Preserve companion bits `[7:6]`. Individual blocks are partly unknown |
| Receive-path pairs | RF `0x73c / 0x740`, `0x798 / 0x79c` | Each pair receives `0x00aac028 / 0x02558000` | The recipe is used, but the meaning of each field is unresolved |

### Frequency tuning

The synthesizer accepts a frequency word independently of Wi-Fi channel
numbers. The `birriasdr_set_center_freq()` call stages the requested center
while idle or applies it during capture. The `birriasdr_get_tuning_range()` call
reports the inclusive command limits, narrowed by any board bounds.
Generic-ID boards start at 2190 MHz because the tested unit could not
calibrate below 2179 MHz. The clock and bias bootstrap keeps the
channel 6 sequence, and the selected secondary oscillator on physical port 0 is
then tuned to the requested center.

| Parameter | Value or rule |
| --- | --- |
| Public center range | 2,156,000,000 to 2,610,000,000 Hz inclusive, or from 2,190,000,000 Hz on generic-ID boards |
| Default center | 2,437,000,000 Hz |
| Request resolution | Integer Hz, rounded to the nearest representable divider word |
| Synthesizer reference | Nominal 60 MHz from the board's 40 MHz crystal profile |
| Oscillator/output relationship | The oscillator runs at twice the requested RF frequency, then divides by two |
| Fractional resolution | 20 bits, nominal step 28.6102294921875 Hz |
| Calibration timing count | `floor(center_hz / 125000) - 2`, constrained to 16 bits |

The nominal frequency relationship is:

```text
center_hz = 60,000,000 × (integer + fraction / 2^20) / 2
```

The driver rounds the entire divider before packing it, so a fractional overflow
carries into the integer field. The selected oscillator uses all 20 fraction
bits for startup, live updates and rollback, while the intermediate bootstrap
oscillators keep the 18-bit recipe. The calibration procedure waits for
completion and latches the resulting range code. Neither completion nor
readback establishes absolute accuracy, PLL lock or sensitivity across the
command range.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Synthesizer selection | RF `0x204[23:22]`, `0x21c[18:17]` | Code 2 during the primary tune, 3 for the secondary | The final selected LO comes from port 0 |
| Synthesizer band profile | RF `0xc00` | Low-band recipe clears `0x3c`, then sets `0x28` | Individual circuit meanings and further divider modes remain unknown |
| Frequency word | RF `0xc68` primary, `0xca8` secondary | Bit 31 is LOAD, with the decoded integer in `[29:20]`. Normal tuning uses fraction `[19:0]` and the bootstrap uses `[19:2]` | The selected port 0 secondary reads `0x0513bbbc` on channel 6. Physical fine-step response remains unmeasured |
| Calibration timing | RF `0xc6c / 0xcac` | Low-band count `floor(center_hz / 125000) − 2`, decoded 16-bit field | The formula belongs to the 60 MHz reference profile, and field limits are not RF limits |
| VCO calibration control | RF `0xcc4[30:29]`, `0xcc8[0]`, `0xd20[2]`, `0xce0` | Ordered start and stop procedure in `run_calibration()` | Not a complete receiver calibration |
| VCO calibration result | RF `0xd7c[21]`, `0xd78[2:0]`, `0xc0c[24:22]` | Poll completion, then copy the result into the range field | Completion is not a qualified lock indication |
| Calibration diagnostics | RF port 0 `0xd70 / 0xd74` | Reject `d74=0xfffff400` and `d74=0x00000400` on normal retunes | Empirical saturation indicators. Full fields and lock semantics are unresolved |

### Changing frequency during capture

The live setter saves the routing, loads the frequency word and calibration
count, runs calibration, restores the routing and verifies the readback. Its
transaction shares a mutex with gain, status and lifecycle operations. The
capture engine, sample clock and sample DMA keep running. Prefer calling it from
a control thread so application callbacks can keep consuming samples while the
register operations complete.

The setter commits the requested center only after success, and the getter
reports that committed request. Buffered samples can still belong to the
previous center. Samples taken during calibration contain a transient, with no
guarantee of phase continuity and no exact transition timestamp. Out-of-range
requests return unsupported without disturbing capture. A failed hardware
update attempts a rollback, leaves the previous center committed and stops the
acquisition. If recovery is enabled, it can then restart with those settings.

Implementation: [mt7921_rf.c](../src/chips/mt7921_rf.c) and
[mt7921_tune.c](../src/chips/mt7921_tune.c).

### Filtering

After gain setup, while capture is stopped, the receiver applies matched analog
selector 1 and digital class 1. It saves all four bandwidth fields, updates only
the masks it owns, verifies the readback and waits 20 ms before GO. A partial
failure restores all saved fields, and a normal reset restores them as well.
Every recovery preparation reapplies the same profile.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Band selection | RF `0x160[29]` | Clear for this 2.4 GHz profile | Setting it alone cannot initialize 5 GHz reception |
| Analog filter profile | RF `0x160[31:30]`, both ports | Bootstrap code 0 and final library profile code 1, saved and restored around each acquisition | Separate from digital bandwidth. Code 1 still has finite out-of-span rejection |
| Digital bandwidth class | MMIO `0x83081000[27:24]` and `0x83091000[27:24]` | Final library profile class 1 with the capture divider unchanged. Owned masks are saved and restored | Greatly reduces rolloff, but neither noise flatness nor the class name guarantees alias rejection |

The complex sample rate stays at 40 MSps, which gives a 40 MHz sampled span.
The filter has finite edge rolloff and stopband rejection, so strong signals
outside that span can alias. On the tested board, the observed noise response
is about 3 dB down at ±18 MHz. That is neither a calibrated swept-signal
response nor a guarantee of alias rejection. The public bandwidth setter
remains unsupported, because neither a filter index nor a class name defines an
independently qualified width or sample rate.

Implementation: [mt7921_filter.c](../src/chips/mt7921_filter.c).

### Gain controls

Manual mode coordinates an analog clamp with several digital gain fields. The
codes are hardware indices rather than calibrated dB, and filter-stage gain does
not select bandwidth. The driver saves the unforced baseline and applies the
analog clamp before the PHY forces, then verifies the readback. When restoring
the baseline before reset, it releases the clamp last.

| Control | Public values | Meaning |
| --- | --- | --- |
| Gain mode | Released (`0`) or manual (`1`) | Release saved overrides or force the requested codes |
| Low-noise amplifier gain | `lna = 0..3` | Analog and PHY LNA index |
| Filter-stage gain | `lpf = 0..8` | Analog and PHY filter-stage index, independent of filter width |
| Digital gain | `digital = 0..12` | Digital PHY index |
| Calibrated gain and global AGC | Unsupported | No calibrated dB mapping or complete gain-loop freeze control |

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Analog override | RF port 1 `0x768` | Force bit `[31]`, LNA field `[30:27]` and filter gain field `[26:23]` | Raw indices that do not independently fix digital gain |
| Gain forces A/B/C | MMIO `0x830000c4` | Force bits `[2:0]`, LNA fields `[10:8]`, `[18:16]` and `[26:24]`, and filter gain fields `[15:12]`, `[23:20]` and `[31:28]` | The combined recipe is implemented, but the independent effect of C remains unqualified |
| Digital gain A/C | MMIO `0x83000108` | Field A at `[29:24]` and field C at `[21:16]`, both set to the requested code | Raw digital index. The independent effect of C remains unqualified |
| Fourth gain force D | MMIO `0x83000150` | Force bit `[31]` and LNA field `[22:20]`, with owned bits `[15:12]` cleared | Its independent contribution remains unqualified |
| Coarse force guard | MMIO `0x830000d0` | Enable bit `[27]` and state `[26:24]`. An already-forced baseline is rejected | Left unchanged. Not an established global AGC-off switch |
| Applied index mirror | RF port 1 `0x268` | Fields for LNA `[23:21]` and filter gain `[20:17]` track the measured manual codes | Index readback only, not a calibrated gain or public control |

### Changing gain during capture

The `birriasdr_set_gain_codes()` and `birriasdr_set_tuner_gain_mode()` calls use
endpoint-zero register transactions while bulk samples keep flowing. After GO,
the original device program never touches the gain registers or the analog SPI
bridge. The host serializes complete gain transactions with tuning and
lifecycle operations, so no new firmware is needed.

The first unforced baseline stays saved across transitions between released and
manual modes. Successful setters commit only verified settings. A failed change
attempts to restore the preceding settings, stops that acquisition and leaves
cleanup to the reader. If automatic recovery is enabled, it reports a gap before
restarting.

The writes are not simultaneous, and buffered samples can precede the change.
A successful setter neither identifies a sample boundary nor proves that the
analog path has settled. Released mode restores the unforced fields, but it
does not establish full automatic gain behavior or guarantee that every internal
gain loop is frozen.

Implementation: [mt7921_gain.c](../src/chips/mt7921_gain.c).

## Capturing with ICAP

The internal capture engine selects a digital tap and writes samples to SRAM
without a CPU copy loop. Its configuration is separate from RF tuning, so a
running producer pointer proves capture activity, not reception of the intended
signal.

The source-mode register at `0x830ad440` uses low-byte mode `0x13`, which
selects the dense single-chain layout without inactive-chain slots. The mux at
`0x830ad448` selects tap 4 for chain 0, enables bit 23 and sets divider bits
`[19:18]` to 3. The programmed low 28 bits are `0x008c0400`, which is the
current 40 MSps profile. The current backend exposes only chain 0.

The current library accepts only 40 MSps, the lowest validated native rate.
Neither native 20 MSps capture nor higher-rate modes are qualified library
settings, and a different filter selector alone does not configure a new
sample clock.

The host also enables the receive and capture clocks, installs the SRAM bounds
and clears the extra packing field. The clock and upstream source changes were
qualified together, and the independent purpose of each enable is unknown. The
host leaves the control word at `0x4f1`, and the MCU writes `0x24f3` only after
GO to start circular capture. At the end, the MCU drains DMA before writing
`0x4f0` to stop the capture path.

The selected mode writes four consecutive complex pairs per 16-byte beat. It
needs neither firmware compaction nor 8-bit conversion. Changing the mode or
packing fields requires rechecking the sample order, stride and producer units,
and the existing decoder deliberately accepts only the known layout.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Receive-only MAC setup | MMIO `0x820e3000` | Clear bit 9, set bit 8 | Part of the qualified startup sequence |
| Capture clocks | MMIO `0x83080004 / 0x83080008` | Set mask `0x3840` | Individual enables are not isolated, and the companion bank is also configured |
| Upstream source setup | MMIO `0x830a1000 / 0x830a1004 / 0x830a1008` | Writes `0x04090100`, low byte `0x10` and zero, respectively | Used with the clock setup, not a fully decoded source map |
| Dense source mode | MMIO `0x830ad440` | Low byte `0x13` with bit 31 set | Consecutive single-chain samples in the selected configuration |
| Capture tap and divider | MMIO `0x830ad448` | Enable `[23]`, divider `[19:18]=3`, tap `[11:8]=4` | Programmed low 28 bits `0x008c0400`, fixed chain 0 profile |
| SRAM packing/grants | MMIO `0x800210b8` | Clear `[19:16]`, set mask `0x9c000000` | The dense path uses no extra packing, and the grant field meanings are incomplete |
| Additional SRAM path setup | MMIO `0x88009004` | Set mask `0x0f000000` | Retained recipe whose individual fields are not isolated |
| Capture control | MMIO `0x80021090` | Setup `0x00f1` → `0x04f1`, live `0x24f3`, final stop `0x04f0` | The full word semantics are not decoded, so do not treat these as independent flags |

Implementation: [mt7921_capture.c](../src/chips/mt7921_capture.c).

## Buffering in circular SRAM

The capture memory spans `0xe0200000` through `0xe023ffff`, a 256 KiB ring
holding 65,536 four-byte complex samples. The low 16 bits of the producer count
sample address units modulo 65,536. These units are not bytes, and the
corresponding byte offset is the sample position multiplied by four.

Each beat has this byte layout:

```text
Q[n], I[n], Q[n+1], I[n+1], Q[n+2], I[n+2], Q[n+3], I[n+3]
```

Each entry is a little-endian 16-bit word that holds a 14-bit two's-complement
component, with its upper two bits set to zero. The host sign-extends negative
components to 16 bits. There is no padding between complex pairs.

At 40 MSps the ring holds only 1.6384 ms. The MCU polls the producer both while
waiting for samples and while waiting for DMA. It accumulates the modulo-65,536
increments into a 32-bit produced count. Only completed packets, not merely
submitted ones, advance the consumed count, because DMA still needs the source
bytes until it completes.

The producer guard fails a run when its poll interval reaches 750 microseconds
or its unread backlog reaches 61,440 samples. These are conservative firmware
limits for this profile, not independent hardware capabilities. A long gap
between polls could hide a complete wrap, and an excessive backlog risks
overwriting data. Larger host buffers cannot recover overwritten SRAM.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Capture bounds | MMIO `0x80021098 / 0x8002109c` | Start `0`, end `0xfffc` | Values for the tested 256 KiB layout, not byte addresses |
| Capture producer | MMIO `0x800210b4[15:0]` | Modulo-65,536 sample position | Must be observed often enough to disambiguate a wrap |
| Producer timing | MMIO `0x89020068` | Microsecond counter used by the MCU guards | Wrap is handled with unsigned subtraction |

Implementation: the `observe_source`, `wait_source` and `wait_space` paths in
[iq_stream.S](../firmware/iq_stream.S).

## Exporting through device DMA

The MCU submits descriptors to its TX0 DMA engine. Here, TX means sending bytes
toward the USB host, not transmitting RF. This engine at `0x5400xxxx` is
separate from the host-interface scheduler at `0x7c024xxx`.

The program allocates four 16-byte descriptors in data memory at `0x02040000`
and four 64-byte header slots at `0x02040100`. Each I/Q descriptor joins two
memory regions: a 44-byte header, and an 8,192-byte SRAM payload followed by
four trailer bytes. The payload address is
`0xe0200000 + (packet_sequence & 31) * 8192`, so successive packets walk the
ring in 2,048-sample chunks.

This program writes the following descriptor:

| Descriptor byte offset | Value | Meaning |
| --- | --- | --- |
| `+0` | Header-slot address | First segment in MCU data memory |
| `+4` | `(44 << 16) \| (1 << 14) \| 8196` | First length 44 and second length 8,196, with the second segment marked last |
| `+8` | Current SRAM payload address | Second segment, including the discarded trailer |
| `+12` | `0` | No additional metadata supplied by this producer |

The program publishes the descriptor contents behind a memory barrier and then
advances the CPU index. The hardware DMA index reports completion. Although the
ring has four entries, the I/Q path waits for each descriptor to complete before
submitting the next one. Serial submission is a constraint of the supported
path.

The trailer can contain a neighboring SRAM word, including the mapped word just
past the ring for the final chunk. It is transport framing and never an extra
sample. The firmware does not copy, scale or reorder the sample payload.
Changing the ring size, chunk size or trailer convention requires coordinated
changes in the assembly, the capture setup and the host parser.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| DMA global control | MMIO `0x54000208` | Busy bits 1 and 3 must clear. Then disable bits 0 and 2, clear bit 30 and enable only bit 0 | Receive DMA stays disabled, and the role of bit 30 is not independently characterized here |
| DMA interrupt mask | MMIO `0x54000204` | Write zero | Completion is polled. This does not disable ROM CPU interrupt service |
| DMA index reset | MMIO `0x5400020c[0]` | Reset the TX0 index | Used before starting the ring |
| Descriptor ring base/count | MMIO `0x54000300 / 0x54000304` | Base `0x02040000`, count 4 | Descriptors live in MCU data memory |
| Published CPU index | MMIO `0x54000308` | Next ring index modulo 4, written after a barrier | Publishes descriptor ownership to hardware |
| Completed DMA index | MMIO `0x5400030c` | Compare with the CPU index to detect drain | Used to release source samples only after completion |
| DMA error status | MMIO `0x54000110` | Copy into the terminal mailbox and require zero | Individual error bit meanings are not decoded here |

Implementation: [iq_stream.S](../firmware/iq_stream.S), especially the
descriptor publication and drain paths.

## Transferring over USB

The library claims the vendor interface identified by class, subclass and
protocol `ff/ff/ff`. Endpoint roles follow descriptor order. The first bulk IN
endpoint carries events and I/Q, the first bulk OUT carries ROM commands, and
the second bulk OUT carries the firmware download. The interface number is
discovered rather than assumed. Register and mailbox accesses use the separate
control endpoint.

The device aggregates events using the current 32 KiB size setting, timeout
code 100 and packet-limit code 30. These settings change how USB transfers are
grouped, not the sample format or sample rate. Each I/Q event is 8,240 bytes:
44 header bytes, 8,192 payload bytes and four trailer bytes. At 40 MSps the
payload throughput is 160 MB/s, and event framing raises it to about
160.94 MB/s before USB protocol overhead.

By default, the native reader keeps 64 transfers of 64 KiB queued. Its event
thread copies completed transfers into a bounded queue and promptly resubmits
them, while the read caller consumes that queue and invokes application
callbacks. Host USB concurrency is independent of the single outstanding device
descriptor. A USB completion can contain part of an event or several events, so
transfer boundaries cannot serve as sample packet boundaries.

The ROM keeps servicing control requests while the original program runs. The
device program accepts GO and STOP through its mailbox. The host also applies
live gain and tuning changes through serialized register transactions on the
control endpoint while bulk sample transfers continue. These updates need no
new firmware download, but their settling transients and older queued samples
still matter. Filter settings remain part of the preparation before GO.
Frequent control polling competes with sample transport. Cleanup cancels and
drains host transfers before freeing buffers or restoring and resetting the
dongle.

| Mechanism | Access / address | Known fields or current use | Limits |
| --- | --- | --- | --- |
| Host-interface WFDMA | MMIO `0x7c024208`, ring setup at `0x7c024600 + 4 × ring` | Global control and per-ring prefetch configuration | Separate from the MCU sample engine. Preserve the boot sequence |
| Host-interface scheduler | MMIO `0x7c026000` block | Quotas and queue mappings set by `configure_dma()` | A full field-by-field scheduler model remains incomplete |
| USB receive flush | MMIO `0x74000018[19]` | Set during reset, then wait for busy mask `0xc0000000` to clear | Separate from normal stream start and stop |
| USB aggregation | MMIO `0x74000018` | Enable `[21]`, size code `[15:8]=32`, timeout code `[7:0]=100` | Current 32 KiB profile. The timeout code is not asserted to be in microseconds |
| USB packet limit | MMIO `0x7400000c[7:0]` | Code 30 | Limits aggregation, not a sample or descriptor count |

Implementation: [usb.c](../src/usb.c), [usb_stream.c](../src/usb_stream.c) and
[mt7921_boot.c](../src/chips/mt7921_boot.c).

## Decoding host I/Q

The host reassembles events across arbitrary USB fragments, then checks their
length, type, sequence and boot nonce. It accepts at most one leftover ROM start
acknowledgment. It rejects gaps, repeats and invalid frames without scanning
ahead for another plausible header, because that would hide loss.

The sample decoder first checks the spare bits of every component, then
sign-extends bit 13 and swaps the wire-order Q,I into native-endian `int16_t`
I,Q. The C API preserves values from −8192 to 8191 without normalization,
averaging, decimation, equalization or an extra digital downconverter.
Applications that need floating-point samples can convert each component and
divide by 8192.

The parser consumes this event layout:

| Event byte offset | Size | Meaning |
| --- | --- | --- |
| `0` | 4 bytes | Packet class 7 in bits `[31:27]` and length 8,236 in `[15:0]`, excluding the trailer |
| `24` | 4 bytes | Event word `0x38000014 + 8192` |
| `28` | 1 byte | Event ID `0xed` |
| `32` | 1 byte | Extended event ID `0xf5` |
| `36` | 4 bytes | Packet sequence, starting at zero and wrapping at 32 bits |
| `40` | 4 bytes | This boot's nonce |
| `44` | 8,192 bytes | Raw Q,I payload of 2,048 complex samples |
| `8236` | 4 bytes | Discarded USB trailer |

All multi-byte fields are little-endian. The library batches converted samples
into application callbacks, 16,384 complex samples at a time by default.
Callback size does not change the device's 2,048-sample packet size. On exit,
the parser must hold no partial event, and the host packet totals must match the
firmware's submitted and completed counts with no DMA errors. Earlier callbacks
may already have delivered a prefix of the data by the time a later error
invalidates the run.

Implementation: [mt7921_frame.c](../src/chips/mt7921_frame.c) and
[stream.c](../src/stream.c). Extension and test guidance lives in
[architecture.md](architecture.md).

## Device memory and firmware mailbox

The following locations are memory or part of our firmware protocol, **not
hardware registers**. Their meaning comes from the included assembly and can
change only together with matching host changes. In particular, the crystal
value below is read from RAM and is not an independent measurement of the
physical clock.

| Location | Purpose | Current interpretation |
| --- | --- | --- |
| `0x00915000` | Program entry in instruction RAM | Original 1,120-byte download image |
| `0x02004600` | Crystal profile value in RAM | Host requires 40,000,000 |
| `0x02040000` | Descriptor ring for DMA | Four slots × 16 bytes |
| `0x02040100` | Event headers | Four slots × 64 bytes, with 44 bytes used per event |
| `0xe0200000..0xe023ffff` | Circular capture SRAM | Room for 65,536 complex samples of four bytes each |

The mailbox base is `0x02038360`. All offsets below are **bytes** from that
base, and every word is 32 bits. The host reads the state first. Once a terminal
state is published, the result fields are stable.

| Byte offset | Owner / direction | Meaning |
| --- | --- | --- |
| `+0` | MCU → host | Boot magic `0x41495242` |
| `+4` | Host → MCU | Fresh nonce, also copied into each event |
| `+8` | MCU → host | Nonce XOR `0xb1771a5d` |
| `+28` | MCU → host | State: 1 ready/running, 2 finite complete, 3 host stop, 4 DMA timeout, 5 GO timeout, 6 initial DMA busy, 8 ambiguous producer timing, 9 source overrun, 10 source timeout |
| `+32` | Host → MCU, before GO | Packet limit, where zero means run until STOP |
| `+36` | Host → MCU | Nonzero requests STOP |
| `+40 / +44` | MCU → host | Submitted / completed packet totals |
| `+48 / +52` | MCU → host | Elapsed timer ticks / DMA error status |
| `+56` | MCU diagnostic | Start timer value |
| `+60` | Host → MCU | Nonzero releases GO after USB reads are queued |
| `+64` | MCU diagnostic | Produced sample units, modulo 2³² |
| `+68 / +72` | MCU diagnostic | Final capture control / last producer position |
| `+76` | MCU → host | Return value of the ROM PHY power-on helper, which the host requires to be zero |
| `+80 / +84` | MCU diagnostic | Maximum unread backlog in samples / maximum producer poll interval in microseconds |
| `+88 / +92` | MCU scratch state | Previous poll timestamp / completed sample units |

## Unimplemented controls

The reserved APIs return `BIRRIASDR_ERROR_UNSUPPORTED`, and their capability
bits stay unset until their hardware behavior is implemented and qualified.

| Control | Current boundary |
| --- | --- |
| Calibrated tuner gain | Raw indices only, with no tenths-of-dB map |
| Global AGC enable/freeze | Manual overrides and baseline release only |
| Independent filter bandwidth | Fixed matched 40 MHz profile only |
| Oscillator ppm correction | No correction API or implicit host mixer |
| Physical antenna selection | Chain 0 is fixed, and connector routing is not exposed |
| User calibration coefficients | No decoded coefficient format or application procedure |
| Other bands, rates and chipsets | No 5 GHz or second-chain receiver, and the MT7925 backend remains unimplemented |

The [architecture guide](architecture.md) describes how to add a backend
without applying this board's register sequence to an unqualified device.
